# Правила написания и организации тестов

## Цель

- Обеспечить предсказуемую проверку логики обработки файлов и отправки email.
- Минимизировать риск регрессий при изменении модулей в `src/`.
- Гарантировать воспроизводимость тестов без зависимости от внешней среды.

## Рекомендуемый стек (обязательный по умолчанию)

- `vitest` — основной тестовый раннер (ESM-first, быстрые моки, удобен для Node.js скриптов).
- `@vitest/coverage-v8` — сбор покрытия через V8.
- `memfs` — изолированное тестирование сценариев файловой системы.
- `vi.mock` / `vi.spyOn` — моки для `nodemailer`, `fs-extra` и других внешних зависимостей.

## Уровни тестирования

### Unit (приоритет: высокий)

- Покрывать чистую и условно-чистую бизнес-логику:
  - `src/common/helper.js`
  - `src/common/constWorkItemResult.js`
  - ветвления в `src/do_work.js` и `src/do_w_item.js` через изоляцию зависимостей.
- Проверять успешные и ошибочные ветки.
- Для каждого публичного экспорта: минимум 1 позитивный и 1 негативный сценарий.

### Integration (приоритет: высокий)

- Проверять взаимодействие модулей:
  - `do_init` + `init_dir` + `init_out_json`
  - `do_work` + `do_w_item`
  - `do_save_out_json` с реальным форматом выходного JSON.
- Использовать временные/виртуальные данные, не обращаться к реальной SMTP-инфраструктуре.

### E2E smoke (приоритет: средний)

- Проверять критичный путь запуска `src/_run.js` на фикстурах:
  - подготовка входных директорий;
  - обработка лицевых;
  - корректная запись итогового `email.json`.
- SMTP всегда мокировать, фактическую отправку писем в E2E не выполнять.

## Приоритетные сценарии для текущего проекта

- `do_w_item`:
  - ошибка чтения/парсинга `email.json`;
  - отсутствие валидного `email`;
  - количество `.htm` файлов не равно 1;
  - успешная сборка конфигурации и вызов отправки.
- `do_work`:
  - пропуск лицевого с `code = Ok`;
  - запись `WorkItemResult(Ok)` при успехе;
  - запись `WorkItemResult(Error)` при исключении.
- `init_out_json`:
  - отсутствие файла `email.json` (должно быть безопасно);
  - валидный JSON;
  - невалидный JSON (ожидаем исключение).
- `do_save_out_json`:
  - успешная запись;
  - проброс ошибки записи.

## Правила для ИИ при генерации тестов

- Использовать русский язык в текстах тестов (`describe`, `it`, `test`) и комментариях.
- Не использовать реальные SMTP-серверы, реальные учетные данные и внешние API.
- Не читать/писать пользовательские рабочие каталоги напрямую: применять фикстуры и изоляцию.
- Не дублировать проверку одного и того же поведения на одном уровне тестов.
- Каждый тест должен проверять одно поведение и иметь понятное название.

## Критерии качества и покрытие

- Минимальное покрытие проекта:
  - `lines >= 85%`
  - `functions >= 85%`
  - `branches >= 80%`
  - `statements >= 85%`
- Для модулей с критичной логикой ветвлений (`do_work`, `do_w_item`): целиться в `branches >= 90%`.
- Pull Request без тестов для измененной логики считается неполным.

## Рекомендуемые команды

- `pnpm test` — запуск всех тестов.
- `pnpm test:watch` — запуск в watch-режиме.
- `pnpm test:coverage` — запуск с отчетом покрытия.

## Шаблон структуры тестов

- `tests/unit/**/*.test.js`
- `tests/integration/**/*.test.js`
- `tests/e2e/**/*.test.js`
- `tests/fixtures/**` — тестовые входные данные.

## Definition of Done для задач с логикой

- Добавлены/обновлены unit-тесты на измененные функции.
- Добавлены/обновлены integration-тесты на измененные связки модулей.
- Для критичных сценариев обновлен E2E smoke (если затронут поток запуска).
- Тесты проходят локально, покрытие не ниже порогов.
